==================================================

十一、从 Brain V0 之后，本轮工作的目标
==================================================

上一份日志结束时，Brain 已经能够稳定输出：

reply
expression
action

但当时 expression / action 还只是“JSON 字段”，尚未真正驱动 JESS 的身体。

本轮目标不是打磨具体表情和动作内容，而是搭建一个可替换、可扩展的执行框架：

Brain
├─ expression → Expression Controller → Expression Driver → Model
└─ action     → Action Controller     → Action Driver     → Animator / Model

核心原则：

1. Brain 只输出“语义命令”，例如 sad / happy / idle。
2. Brain 不直接知道 BlendShape 名、骨骼名、VRM API 或 Animator 细节。
3. Controller 负责稳定的 JESS 语义接口。
4. Driver / Adapter 负责把语义翻译成“当前模型真正能执行的操作”。
5. 未来从当前 VRM 换成 Blender/GLB 模型时，优先替换 Driver 和模型映射，而不是重写 Brain。

这意味着目前正在搭建的是“形式骨架”，而不是最终角色内容。

==================================================
十四、重要 Debug：为什么直接写 BlendShape 会失效
==================================================

曾尝试通过：

SkinnedMeshRenderer.SetBlendShapeWeight(...)

直接修改 Face 的 BlendShape。

现象：

代码可以执行，但运行时权重会被重新写回 0。

原因定位：

当前 VRM 1.0 模型的表情状态由 Vrm10Instance / UniVRM Runtime Expression 系统管理，
并在运行过程中持续更新。

因此直接写底层 BlendShape 会与 VRM Runtime 的所有权发生冲突。

最终改为使用 UniVRM 1.0 的运行时接口：

vrmInstance.Runtime.Expression.SetWeight(
    ExpressionKey.Happy,
    1.0f
);

该方案验证成功。

结论：

对当前 VRM 模型：
应通过 VRM Runtime Expression API 驱动表情，而不是直接写 BlendShape。

对未来普通 Blender/GLB 模型：
如果没有 VRM Runtime 接管，则可以使用直接 BlendShape Driver。

这也是后续建立 Driver 抽象层的重要原因。

Brain → ActionController → ActionDriver → Animator
正式接通。


==================================================
二十六、一个值得保留的 Debug 经验：Inspector 引用与代码变量
==================================================

例如：

[SerializeField]
private JessActionController actionController;

它并不会“创建一个 JessActionController”。

它只是声明：

JessBrain 需要一个 JessActionController 的引用。

真正由哪个 Unity Component 提供这个引用，
需要在 Inspector 中连接。

因此以后出现：

Object reference not set to an instance of an object

尤其是在刚新增 SerializeField 之后，
优先检查 Inspector：

是否仍然显示 None。

本轮就是标准案例。
